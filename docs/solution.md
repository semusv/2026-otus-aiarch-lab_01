# Домашнее задание №1
## Разработка стратегии, оценка рисков и дорожной карты AI-проекта

### Цель:
разработать стратегию внедрения AI-решения с выбором контрактной модели, оценкой рисков и дорожной картой для согласования с заказчиком.


## Шаг 1. Проанализировать вводные и составить список вопросов, без ответов на которые нельзя начинать проект.

### Вопрос 1 : Данные о поведении пользователей

*«В каком формате и с какой частотой доступны сырые логи поведения (клики, скроллы, время на странице)? Есть ли возможность выгрузки из GA в DWH или логи пишутся локально?» И есть ли утвержденная схема событий (event schema) или методология: какие действия пользователя (клик, добавление в избранное, просмотр >30 сек) считаются сигналом интереса для модели?*

**Почему это важно:**

- Без сырых логов невозможно обучить персонализированную модель (GA даёт агрегированные данные).
- Если логи отсутствуют, потребуется 2–4 недели на настройку сбора → сдвигает срок PoC.
- Риск: «Мусор на входе = мусор на выходе» → модель не покажет качество, проект закроют.

### Вопрос 2: Интеграция офлайн-данных

*«Как мы связываем пользователя между сайтом и офлайн-магазином (по номеру телефона, карте лояльности, email)? Как часто покупки из 1С должны исключаться из рекомендаций – допустима ли задержка 15–30 минут или нужно real-time (< 1 минуты)? Есть ли API для единой интеграции?»*

Почему это важно:

- Требование «омниканальности» бессмысленно без синхронизации офлайн-покупок.
- Битрикс + 1С — сложная интеграция; без четкого контракта данных возрастает риск рассинхрона.
- Риск: клиент видит рекомендацию уже купленного товара → падение доверия к системе.

### Вопрос 3: Latency + GenAI trade-off

*«Требование <200ms относится только к выбору товаров или включает также генерацию текстового описания LLM? Допустимо ли асинхронно подгружать сгенерированный текст или использовать кэширование шаблонов?»*

**Почему это важно**:

- Генерация текста на LLM обычно занимает 500–2000ms. Если это входит в лимит 200ms — технически невыполнимо без компромиссов.
- Ответ определит архитектуру: синхронный RAG-пайплайн или асинхронная очередь + кэш.
- Риск: нарушение SLA → падение конверсии, конфликт с CTO.

### Вопрос 4: Метрика успеха и атрибуция

*«Каков текущий средний чек (AOV) и конверсия блока рекомендаций (укажите, как именно измеряется: клик / добавление в корзину / покупка)? Какую методику атрибуции вы готовы утвердить, чтобы мы могли доказать, что рост AOV на 10% – это результат именно AI? Готовы ли вы выделить holdout-группу (например, 5% пользователей, которые продолжат видеть старые rule-based рекомендации) на время A/B-теста (минимум 2-3 недели)?»*

**Почему это важно**:

- Без базовых метрик невозможно измерить эффект от внедрения.
- Без методики атрибуции (A/B-тест, holdout-группа) заказчик может не признать результат.
- Риск: «Мы не видим роста» → проект закрывают, несмотря на технический успех.

### Вопрос 5: Границы безопасности и PII

*«Какие именно поля считаются персональными данными (ФИО, телефон, email, cookie_id)? Допускается ли передача обезличенных данных в облачные API (например, для эмбеддингов), или требуется строгий on-prem контур для всех этапов?»*

**Почему это важно**:

- Определяет выбор стека: публичные API (дешево, быстро) vs self-hosted LLM (дорого, сложно).
- Влияет на бюджет: on-prem требует GPU-кластера и MLOps-команды.
- Риск: утечка ПДн → штрафы по 152-ФЗ, репутационный ущерб, остановка проекта.

### Вопрос 6: Про бюджет эксплуатации / OpEx

*«Какой месячный бюджет (OpEx) вы готовы выделить на эксплуатацию системы после запуска? Сюда входят: облачные GPU / API-токены, хранение векторной БД, мониторинг, логирование, возможные дообучения модели. Например, до 200 тыс. руб. в месяц или 500 тыс.?»*

**Почему это важно:**

- Архитектурный выбор: От этой цифры напрямую зависит, сможем ли мы использовать LLM для генерации описаний (дорого: $0.01–0.05/запрос) или ограничимся шаблонами + пост-обработкой. Также это определяет выбор между SaaS-API (линейная стоимость, нет DevOps) и self-hosted (фиксированные затраты, но нужен GPU-кластер и MLOps-команда).
- Расчёт TCO: Согласно методологии курса, TCO = CapEx + (OpEx × 36m). Без оценки ежемесячных расходов мы не можем предложить реалистичную дорожную карту: например, запуск MVP на 5% трафика может стоить 50 тыс./мес, а масштабирование на 100% — уже 400 тыс./мес.
- Защита бюджета: Если не зафиксировать OpEx-лимит на этапе пресейла, после запуска возникнет конфликт: CFO увидит счёт за токены на 300 тыс. руб. и потребует остановить проект. Вопрос позволяет заранее согласовать модель Capped OpEx или Budget Gate на каждом этапе масштабирования.
- Связь с рисками: Риск «рост стоимости инференса» имеет высокий Exposure (P=40%, I=высокий). Зная лимит, мы можем заранее заложить митигации: semantic caching (Redis/Qdrant), model routing (простые запросы → дешёвая модель), quantization (4-bit inference).

### Вопрос 7: Инфрастуктура развертывания

*«Какова целевая инфраструктура для Production-окружения: предпочитаете ли вы managed Kubernetes в облаке, готовы ли рассматривать serverless-архитектуру для отдельных компонентов, или есть требование к полностью on-prem развертыванию?»*

**Почему это важно:**

- Определяет выбор стека: Helm-чарты vs Docker Compose vs Serverless Framework.
- Влияет на бюджет: managed K8s ≈ $100–300/мес за control plane + узлы; on-prem — CapEx на железо + команда поддержки.
- Определяет MLOps-пайплайн: CI/CD для K8s (ArgoCD/Flux) vs деплой в Functions.
- Риск: если клиент хочет «как у всех в облаке», но по 152-ФЗ данные не могут покидать контур — потребуется гибридная архитектура (данные on-prem, инференс в защищённом облаке).

### Вопрос 8: Золотой датасет

*«Есть ли у вас эталонный набор данных (Golden Dataset) из 100–500 пар “пользователь / сессия → товар, который реально купили”? Если нет – кто и в какие сроки готов его разметить?»*

**Почему важно:**

- Без этого мы не сможем объективно измерить качество модели до A/B‑теста.
- Заказчик сможет бесконечно говорить «мне не нравится», даже если код работает.
- Влияет на контракт: без золотого датасета Fixed Price на MVP невозможен.

## 📋 Шаг 2. Выбор модели контракта и обоснование для стейкхолдеров

### 🧭 Общая стратегия: Поэтапное контрактование (Phased Contracting)

В AI-проектах с высокой стохастичностью единый `Fixed Price` на весь цикл ведет к кассовым разрывам или провалу по качеству. Мы применяем модель, где **контракт адаптируется под ширину «Воронки неопределенности»**: от разведки данных до масштабирования с управляемым `OpEx`.

---

### 🔹 Фаза 0. Data Discovery (2–3 недели)

**Модель контракта:** `Fixed Price` (малый бюджет, жесткий скоуп)

| Стейкхолдер | Обоснование (аргументы для диалога)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **CEO**          | *«Мы не начинаем бурение, не проведя геологоразведку. За фиксированную сумму вы получаете отчет по качеству данных, утвержденный `Golden Dataset` (100–500 эталонных пар) и точный прогноз `TCO`. Это защита от инвестиций в проект, где данные изначально непригодны для ML. Без Discovery оценка PoC будет гаданием, а с ним — математикой.»* |
| **CTO**          | *«Аудит проводится в изоляции, без вмешательства в ядро Bitrix и 1С. Мы формализуем контракт данных (API schema, event schema, частоту синхронизации), согласуем границы ПДн (152-ФЗ) и выбираем контур (cloud/on-prem) до написания кода. Результат — готовый blueprint интеграции, который исключит рефакторинг монолита на старте.»*                                |

### 🔹 Фаза 1. PoC (Proof of Concept) (1.5–2 месяца)

**Модель контракта:** `Capped T&M` (Time & Materials с потолком бюджета)

| Стейкхолдер | Обоснование (аргументы для диалога)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **CEO**          | *«Максимальная неопределенность еще не снята, поэтому мы делим риск пополам. Вы платите за фактические часы работы экспертов, но бюджет жестко ограничен (`Cap`). Если гипотеза не подтвердится на `Kill Gate`, мы останавливаемся, экономя до 70% бюджета. Вы покупаете не "магию", а ответ на вопрос: "Решаемо ли это технически и экономически?"»* |
| **CTO**          | *«PoC строится в песочнице. Мы проверяем критические технические гипотезы: укладываемся ли в latency <200ms при GenAI (через semantic caching/async), дает ли пайплайн `Faithfulness >0.8` на Golden Dataset, выдерживает ли нагрузку прототип. Скорость валидации важнее качества кода на этом этапе. Мы фиксируем остаточные риски и точный план MVP.`*                                             |

### 🔹 Фаза 2. MVP (Minimum Viable Product) (2–3 месяца)

**Модель контракта:** `Поэтапный Fixed Price` (спринты 2–4 недели)

| Стейкхолдер | Обоснование (аргументы для диалога)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **CEO**          | *«Неопределенность сужена: данные готовы, стек выбран, пайплайн работает. Теперь мы переходим на короткие фиксированные итерации. Каждый спринт привязан к измеримой бизнес-метрике (CTR, конверсия в корзину). Бюджет предсказуем. Любая новая "хотелка" маркетинга оформляется через `Change Request` с явным пересчетом TCO — никакого скрытого раздувания бюджета (`Scope Creep = Budget Creep`).»* |
| **CTO**          | *«MVP разворачивается как отдельный микросервис с четкими API-контрактами. Мы внедряем базовый MLOps, логирование и мониторинг. Техдолг (осознанный на PoC) ведется в бэклоге и погашается по плану. Интеграция с Bitrix идет через неблокирующие вызовы, гарантируя zero-downtime. Критерии приемки теперь объективны: метрики Golden Dataset + A/B-тест на 5% трафика.`*                                                                 |

**Модель контракта:** `T&M + SLA` (с жестким `OpEx`-лимитом и FinOps)

| Стейкхолдер | Обоснование (аргументы для диалога)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **CEO**          | *«Система переходит из статуса R&D в стратегический актив. Мы переходим на модель поддержки с гарантированным SLA. `TCO = CapEx + (OpEx × 36m)`. Месячный бюджет на инференс, векторную БД и ретрейны зафиксирован заранее. Внедренные механизмы FinOps (model routing, quantization, semantic caching) держат стоимость запроса в рамках утвержденного лимита. Вы платите за стабильный рост AOV, а не за непредсказуемые счета за токены.»* |
| **CTO**          | *«Фокус на отказоустойчивости и автоматизации. Развернут полноценный CI/CD, автоматический retrain при data drift, мониторинг latency p95 и ошибок. Безопасность (152-ФЗ) встроена в архитектуру: PII маскируется на входе, данные не покидают контур. Система соответствует SLA 99.9%. Команда интегратора передает знания и документацию вашей команде поддержки.`*                                                                                                     |
